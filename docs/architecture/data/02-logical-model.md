# 2. Canonical logical data model

The entity catalog is machine-readable in [model/model.json](model/model.json) (204 entities). Per-entity reference: [generated/logical-model.md](generated/logical-model.md). Diagrams: [generated/er-diagrams.md](generated/er-diagrams.md). This document defines the conventions every entity follows, so the catalog can state only what is specific to each entity.

## 2.1 How to read an entity entry

| Property | Meaning |
|---|---|
| `module` | Authoritative owner. Only this module writes the table. |
| `scope` | One of `platform`, `workspace`, `brand`, `workspace_or_brand`, `personal`, `personal_brand_optional`, `inherited`. This fixes which scope keys exist ([§2.4](#24-scope-keys)). |
| `addressable` | The record has an envelope row in `core.record` (public ID, lifecycle, scope, provenance) and can be linked, mentioned, followed, shared, commented on, searched, trashed, and restored independently ([§2.3](#23-the-record-envelope)). |
| `containment_parents` | Possible owning containers. A row has **at most one** at a time. Containment cascades lifecycle and never crosses brands ([03](03-tenancy-brand-sharing.md)). |
| `extends` | 1:1 typed detail of another entity (for example `agent_run` extends `execution.operation`). |
| `associations` | Non-owning references. They never cascade lifecycle and never grant access. |
| `lifecycle` | `full` (archive/trash/restore/purge via `core.record`), `trash`, `mutable`, `state-machine`, `append-only`, `versioned-immutable`, `ephemeral`. |
| `concurrency` | `row-version`, `field-merge`, `ordered`, `locked`, `append-only`, `cas` ([09](09-concurrency-consistency.md)). |
| `retention_class`, `confidentiality`, `export`, `search_ai`, `may_contain_secrets`, `personal_data`, `volume` | Classification ([11](11-data-classification.md)) |
| `uniqueness`, `key_columns`, `sensitive_fields` | High-value typed columns and constraints. The list is **not exhaustive**: presentation-only fields are left to implementation briefs. |
| `requirements` | Representative requirement IDs from the 0A catalog that the entity serves |

## 2.2 Identifiers ([ADR-02](12-decisions.md#adr-02))

| Identifier | Form | Where | Exposed? |
|---|---|---|---|
| Internal key `id` | UUIDv7, generated by the application before insert | Primary key of every table | **Never** in URLs or APIs |
| Public ID | `<prefix>_<26 Crockford base32 chars>` encoding 128 random bits (e.g., `tsk_0J8Z…`). The prefix is the record type (model `public_id_prefix`). | `core.record.public_id` for addressable records; a `public_id` column on other API-visible tables (comments, time entries, test results) | Yes: URLs, API, exports, webhooks |
| Idempotency key | Client-supplied string | `execution.idempotency_key` | Echoed only |
| External ID | Provider's ID | `integrations.external_identity` | Shown as provenance |

Public IDs are random, so they reveal no counts, tenants, names, or creation order. Internal UUIDv7 keys give B-tree locality and let the application create IDs before insert (offline capture, idempotent creates, batch imports). They are never exposed, because they encode a timestamp. Public IDs never change, including across brand moves and restores.

## 2.3 The record envelope

`core.record` is a thin supertype row for **addressable** records. It carries identity, scope, lifecycle, and provenance, and **no domain fields** ([ADR-03](12-decisions.md#adr-03)). It exists so that reusable primitives (shares, links, mentions, followers, labels, comments, attachments, custom-field values, search documents, review subjects, tombstones) can hold a **real foreign key** to "any addressable record" without an untyped universal table.

```
core.record (id, public_id, record_type, workspace_id, brand_id, scope_key, owner_membership_id,
             lifecycle_state, archive_cause, archive_batch_id, deletion_batch_id, prior_lifecycle_state,
             archived_at, archived_by, trashed_at, trashed_by, purged_at,
             source_kind, source_ref, template_installation_id,
             created_at, created_by_actor_type, created_by_actor_id, updated_at, version)

work.task   (id → core.record.id, workspace_id, brand_id, scope_key, lifecycle_state, …typed task columns…)
            FOREIGN KEY (id, workspace_id, scope_key, lifecycle_state)
              REFERENCES core.record (id, workspace_id, scope_key, lifecycle_state)
              DEFERRABLE INITIALLY DEFERRED
```

- The typed row and the envelope are created in the same transaction. The deferrable composite foreign key guarantees they agree on workspace, brand scope, and lifecycle at commit.
- `record_type` is a fixed enum of the 30 addressable types in the model (brand, team, workflow, project, milestone, task, decision record, Inbox item, note, intake form, work block, document, file, deliverable, goal, key result, portfolio, saved view, dashboard, report definition, connection, webhook subscription, test case, test suite, test run, environment, release, template, automation, agent profile).
- High-volume child data (comments, checklist items, field values, test results, attempts, audit events, notifications, time entries) is **not** registered. These rows hang off a registered host instead.
- The envelope row **survives purge** as a tombstone: content columns are cleared and `lifecycle_state = 'purged'` ([08](08-deletion-retention.md)).

## 2.4 Scope keys

| Scope | Columns | Constraint pattern |
|---|---|---|
| `platform` | none (a `workspace_id` may be kept as a plain reference, e.g., `billing_account`) | Not tenant-filtered; accessed by platform roles or through tenant-facing views |
| `workspace` | `workspace_id NOT NULL` | `FOREIGN KEY (workspace_id) REFERENCES tenancy.workspace` |
| `brand` | `workspace_id`, `brand_id NOT NULL`, `scope_key = brand_id` | `FOREIGN KEY (workspace_id, brand_id) REFERENCES tenancy.brand (workspace_id, id)` |
| `workspace_or_brand` | `workspace_id`, `brand_id NULL`, `scope_key GENERATED ALWAYS AS (coalesce(brand_id, workspace_id)) STORED` | Brand foreign key as above (skipped when null). `scope_key` lets containment foreign keys require the same brand **or** the same workspace-level scope. |
| `personal` | `workspace_id`, `owner_membership_id NOT NULL` | `FOREIGN KEY (workspace_id, owner_membership_id) REFERENCES tenancy.membership (workspace_id, id)` |
| `personal_brand_optional` | `personal` + `brand_id NULL` | As above. A brand is required by the triage command, not by the table. |
| `inherited` | Parent's keys duplicated: always `workspace_id`; `brand_id`/`scope_key` when the parent has them | Composite foreign key to the parent including the scope columns ([03 §3.3](03-tenancy-brand-sharing.md#33-database-enforced-invariants)) |

Workspace and brand IDs are both UUIDs from the same generator and never collide. A `scope_key` therefore identifies exactly one brand or one workspace-level scope.

## 2.5 Standard columns

Every tenant table has the columns for its scope plus:

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | UUIDv7 primary key |
| `created_at`, `updated_at` | `timestamptz` | Set by the database (`now()` at statement time). `updated_at` is maintained by the owning module, not a trigger, so bulk jobs control it. |
| `created_by_actor_type`, `created_by_actor_id` | `actor_type` enum, `uuid` | `human`, `ai`, `automation`, `integration`, `agent`, `system` (0A actor types). AI actions record the person on whose behalf they ran in audit. |
| `updated_by_actor_type`, `updated_by_actor_id` | same | Last writer, for conflict display (ST-06). The full history is in audit. |
| `version` | `bigint` | For `row-version` and `field-merge` entities. Incremented on every update. |
| `source_kind`, `source_ref` | enum, text | On the envelope for addressable records; on the row for others where creation channels vary (typed, paste, voice, email, form, API, webhook, import, integration, AI proposal, agent, automation, template, sample). |
| `operation_id` | `uuid` | Where a row was produced by a logical operation (imports, AI applications, agent runs, automation runs, brand moves). Enables "show everything this operation changed" and bulk undo. |

Append-only tables omit `updated_*` and `version`. Execution detail tables take state from `execution.operation`.

## 2.6 Typed, not universal

- Business records are **typed tables** with typed columns for every field used in filtering, sorting, policy, or lifecycle. Examples: `status_id`, `status_category`, `due_date`, `brand_id`, `priority`, `assignee`.
- **JSON (`jsonb`) is allowed only** for:
  - validated, versioned definitions (workflow revisions, query ASTs, automation versions, template packages);
  - provider payloads kept for provenance;
  - redacted error details;
  - snapshot evidence (readiness snapshots, daily records).
  Each has a schema version field and is validated by the owning module. JSON fields never carry authorization keys ([10 §10.6](10-postgresql-guidance.md#106-json-policy)).
- Custom fields use the typed value table `workflow.field_value`, with one typed column per value kind. It is not an untyped attribute–value store ([04 §4.6](04-relationship-primitives.md#46-custom-fields), [ADR-06](12-decisions.md#adr-06)).
