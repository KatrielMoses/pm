## Decisions

| # | Topic | Decision |
|---|---|---|
| S1 | One authority, applied first | Every read of the index is one SQL statement that joins a projection row to the `core.record` that governs it and applies the **compiled visibility predicate** (`need: view`, with project chains, exact-record shares, brand sensitivity, and lifecycle) *before* the row is matched, ranked, counted, faceted, excerpted, or remembered. There is no second evaluator and no application-side filtering of a page that was fetched without it. A hidden record contributes to no number, order, facet, or excerpt, and a hidden and an unknown record produce the same response down to the same statements (`not_found` for opening, `unavailable` for a filter naming one). A matrix test compares each person's search results with the owning module's own single-record read for every record, so the two authorities cannot drift. |
| S2 | The index is a projection, never a source of access | `search.search_document` holds one row per searchable source row: its kind, its identifier, its title and body text, a time, and an optional owner. It stores **no** brand, project, lifecycle, or permission key. It names the record whose access governs it (`auth_record_id`: itself, or the host of a comment, file, or deliverable) and the record that opens it in context (`context_record_id`); both are read live. A change of brand, project, share, role, or lifecycle therefore takes effect at once and never needs a re-index. This amends the 0B sketch (a projection carrying scope and permission keys) because denormalized keys are exactly what revocation (I-12) cannot trust. Rows are rebuildable from the sources at any time. |
| S3 | Registered sources only | Text enters the index only through a `SearchSource` adapter in a registry (kind, label, `load`, `publicIds`, `resolve`, an optional live check). 5A registers: projects, tasks, milestones, decisions, documents (the text of the **current saved version**), comments, files (the name), and deliverables (the title and the submission note). A later phase adds a source (goals, people, integration records, attachment text) by registering one; the database checks only the shape of the kind. Never indexed: custom field values (field policy), live drafts and operations (nothing unsaved is searchable), restricted reference labels (a reference contributes no text), file bytes, inbox items and notes (personal, 2E), and secrets. |
| S4 | Live checks beside the lag | Where the source row carries its own state, the query checks it as well (a deleted comment, a trashed file or deliverable), because the index may lag: such a result disappears with the change, not with the next index run. Trash, archive, and restore need no re-index (lifecycle comes from the governing record); a purge removes the record's rows and every row it hosts in the same statement that tombstones it, and deleting a source row removes its row (database triggers, so no write path can miss it). `state` filters (`active`, `archived`, `any`) choose among states the person may already see. |
| S5 | Feeding the index: keys in the source's transaction, content in the worker | An `AFTER` trigger on each source table writes only a **key** (`search.index_status`: kind, id, governing record) in the same transaction as the change, so a change and its queue entry commit together or not at all and no write path (API, worker, purge, import) can miss one. The worker job `search.index` (every ten seconds, discovery by payload-free definer function) claims keys with `FOR UPDATE SKIP LOCKED`, rebuilds the row from the source of truth under a savepoint, and drops the key; a source that is gone, purged, or deleted removes its row. A change that lands while a row is being indexed waits behind the claim, queues again, and is indexed again, so the row converges to the latest text. Existing rows are queued by the migration itself: the source tables force row-level security even on the migration role, which would read no rows, so the migration lifts the force on those eight tables for that one read inside its own transaction, queues every source row (idempotent), checks the deferred keys, and forces security again (a database that already holds records is found complete only after the backlog is indexed, and says `catching_up` until then; corrective review 01 of Phase 5C). The 0B text said "fed by outbox consumers"; that is replaced because events carry no content, are not emitted for every edit, and cannot be backfilled. |
| S6 | Bounded, retryable, observable | Each run indexes at most `SEARCH_INDEX_BATCH_MAX` keys per workspace in separate transactions (a poison row never blocks or rolls back the others) and visits at most `SEARCH_INDEX_DISCOVERY_MAX` workspaces. A failed attempt keeps its key with an attempt count, a short code (`source_error`, `invalid_content`, `timeout`, `unknown_source`; never a message), and the next time (`SEARCH_INDEX_BACKOFF_SECONDS`, doubling); after `SEARCH_INDEX_MAX_ATTEMPTS` the key is `failed` and retried every `SEARCH_FAILED_RETRY_MINUTES` until it succeeds. Metrics `search.index.jobs` (kind, outcome) and `search.query.duration`; logs carry the kind and error class only. Indexed text is cut at `SEARCH_BODY_MAX_CHARS`. |
| S7 | Truthful state, never complete when it is not | Each response carries the workspace index state for **this person**: `complete`, `catching_up` (keys waiting), or `degraded` (keys failed), computed only over keys whose governing record the person can read, so a hidden edit leaves no trace. Each result says `current`, `updating`, or `failed` ("may be out of date"). `GET search/status` returns the same state and the registered sources. The search page shows a banner (and the oldest wait) rather than presenting a lagging index as complete, and administrators see persistent failures on Home (IA-10). A person whose view is complete sees nothing extra. |
| S8 | Query language and matching | Words are all required; `"a phrase"` keeps its order; `-word` excludes; a word with punctuation inside is a phrase of its parts; the last positive word also matches by prefix (the word being typed, unless quoted). ASCII punctuation separates words on both sides (the index and the parser use one rule), so `report.final.pdf` is found by `report`; every other character is kept, so any language is indexed. Two configurations are indexed together (**DQ-24 resolved**): `simple` (no stemming or stop words, prefixes) and `english` (stemmed). Every token is quoted into the `tsquery`, so no input can add an operator. Limits: `SEARCH_QUERY_MAX_CHARS`, `SEARCH_TERMS_MAX`. A query with only exclusions or punctuation is refused, never "everything". |
| S9 | Ranking, counts, facets, paging from one authorized set | Title matches weigh more than body matches (`ts_rank_cd`, weights A and B); ties break by time then key, so the order is total. The page, the total, and both facets are read from one materialized set of authorized matches in **one pass**; a facet counts what choosing another value would give (the kind facet ignores the kind choice, the brand facet the brand choice). Counts stop at `SEARCH_COUNT_MAX` and say "at least". Paging is **keyset** (0B §10.5 forbids offsets for user lists): the cursor holds the last result's rank, time, key, and position, is signed for one person and one search (`cursor_invalid` otherwise), and depth stops at `SEARCH_RESULTS_MAX`. Page size is at most `SEARCH_PAGE_SIZE_MAX`. |
| S10 | Excerpts and marks as data | The server returns excerpts and titles as parts (`text`, optionally `hit`), computed only for rows that already passed S1, around the first matching word, with whitespace collapsed and at most `SEARCH_SNIPPET_CHARS` characters; the client renders them as text (`<mark>` for a hit), never as markup. `ts_headline` is not used: it does not see the punctuation rule of S8. A hit stemmed away from the shown words is honest: the excerpt then starts at the beginning of the text, unmarked. |
| S11 | Filters resolve against what the person can see | Type, brand, project, state, a recency window, "created or owned by me", and "comments that mention me". A named brand or project is resolved against the viewer's visible set; one that is hidden is refused exactly as one that does not exist (`unavailable`). The owner filter is "me" only: filtering by another person needs a people picker that does not exist yet (honest deferral, with the filter's other four IA-10 criteria complete). Each result names its type, brand, project, owner, and last update (SRCH-006); the person's name appears only to members (guests see none). |
| S12 | Opening re-checks and never widens | A result opens through `POST search/open`, which resolves the public identifier through the source and repeats S1 and S4 at that moment (one `not_found` for hidden, deleted, purged, trashed, or unknown, produced by the same statements), then the destination page authorizes again. A comment, file, deliverable, milestone, or decision opens the record that holds it, and only when the viewer can see that record. Scrolling to and highlighting the match inside the destination is **not built**: comments are paginated and no destination can address one comment or a passage (ADR-0027 C13). |
| S13 | Recent searches are personal, bounded, and honest | Only a submitted search is remembered (the page's Search, or the palette's "Search everywhere"); typing, lookups, and filter changes are not. At most `SEARCH_RECENT_MAX` per person and workspace; each is kept `SEARCH_RECENT_RETENTION_DAYS` (swept by the index job) and is erased with the person's other personal data. What is stored is the person's own words and filters, never results. When listed, filters naming a brand or project are checked again, and a search naming a place the person can no longer see is left out. A person can forget one or all. Never audited, never copied into events. |
| S14 | Why there is no full-text (GIN) index, and the bound | Under the forced tenant-isolation policy PostgreSQL cannot use a GIN index on `tsv` for a role subject to it: the match operator is not *leakproof*, so it may not run ahead of the policy (verified with `EXPLAIN` as `app_rw`: a scan filtered by workspace, with or without the index), and marking it leakproof needs a superuser, which no role has. An unused index would only slow every write, so none is created. The cost of a search is therefore proportional to **one workspace's** entries, paid once per request (S9's single pass). Measured at 60,000 entries: roughly 60 ms when nothing matches and 250 to 400 ms for a term matching everything. Upgrade path, when a workspace nears 100,000 entries (watch `search.query.duration`): a reviewed definer function owned by a role with a narrow policy, or per-workspace partitions; either needs an architect decision because it adds a privileged read path. |
| S15 | Where search lives | The page `/workspaces/{ws}/search` keeps its whole state in the address (a deep link is a search; Back restores it). Its default scope is the shell's brand scope with one click to "Search all my brands" (IA-10); the query string is the page's own state, so the shell does not re-read the workspace on each filter change. The command palette adds "Search everywhere for …", up to six permission-aware results (deduplicated against its record list), and recent searches before anything is typed; `/` opens the page (single-key shortcuts), and `go.search` is a registered command. Keyboard only, 320 px and 200% zoom, forced colours, reduced motion, offline recovery, and revocation are tested in the browser. |
| S16 | Honest absences | Not built in 5A: concept or semantic search and AI query interpretation (OD-31, 7B), attachment text and OCR (OD-31), people, goals, inbox, notes, and integration records as sources (later phases register them), typo tolerance, saved searches and alerts, search analytics and metric semantics (5C), external connectors (6x), cross-workspace search, scrolling to a match (S12), an owner filter for other people (S11), and a GIN index (S14). |

## Consequences

Migration `0041_permission_aware_search` reverses exactly to 0040 (three tables, the source triggers and their functions, the discovery function, and the schema). The API gains `GET search`, `GET search/status`, `POST search/open`, and `GET/POST/DELETE search/recent` (PL-38); the worker gains the `search.index` job. Existing rows are queued at migration time and indexed by the first worker runs; until then every response says `catching_up`. Adding a searchable kind later means registering a source and a trigger, never changing the authority.
