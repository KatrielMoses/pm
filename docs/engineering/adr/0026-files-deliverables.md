## Decisions

| # | Topic | Decision |
|---|---|---|
| F1 | Storage and scanner ports, honest when absent | A provider-neutral `ObjectStorage` port (presign `PUT` and `GET`, head, bounded read, copy, idempotent delete, readiness check) with two adapters: S3-compatible storage signed with SigV4 and no SDK, and a local filesystem adapter with HMAC-signed URLs for development and tests, refused when `APP_ENV` is deployed. `OBJECT_STORAGE` defaults to `none`. A `MalwareScanner` port has a ClamAV `INSTREAM` adapter and an EICAR-only test adapter (refused when deployed); `MALWARE_SCANNER` defaults to `none`. `GET …/storage` and readiness report `object_storage` truthfully: `ok`, `not_configured`, or (configured but unreachable) `fail`. Without storage or a scanner, upload initiation is `dependency_unavailable` with `storage_not_configured` or `scanner_not_configured`; nothing is ever reported as stored or scanned. External links need neither. |
| F2 | Keys and signed URLs | Object keys carry no names and no identifiers: `q.{64 random hex}` in quarantine, and `o.{same}` once promoted after a clean scan; the database row binds a key to its workspace. A signed URL is issued per authorized request, bound to the key, the operation, and the expiry (and for uploads the exact length, type, and checksum), and lasts `SIGNED_URL_LIFETIME` (default 300 seconds). Signed URLs are never stored, logged, or emitted in events, notifications, or exports; downloads are `303` with `Cache-Control: no-store`. The residual use of an issued URL until it expires is the accepted 0D residual risk (PC-03). |
| F3 | Upload sessions | Initiate (`Idempotency-Key`) checks `record.upload` on the host, the allow-listed content type and that the file name's extension agrees with it, the size (at most `FILE_UPLOAD_MAX_BYTES`), and reserves the bytes against the quota under a row lock, then returns a session (`upl_`) with a signed `PUT`. Complete re-checks authority and verifies presence, size, SHA-256, and type in storage: a missing object is the retryable `file_not_ready` (`missing_object`); a mismatch rejects the session (`checksum_mismatch`, `size_mismatch`, `type_mismatch`), deletes the bytes, and releases the reservation. An idempotent replay returns the same session with a freshly signed URL. A sweep expires sessions past `UPLOAD_SESSION_LIFETIME`, releasing the reservation and the quarantined object. A session answers only its creator. |
| F4 | Malware scanning, fail closed | Completion enqueues one scan job per object. Scanner or storage failures retry with backoff; the last of `FILE_SCAN_MAX_ATTEMPTS` marks the object `error` (shown as blocked, scan failed), deletes its bytes, and releases its quota. An infected object is blocked, its bytes deleted, and its quota released; the signature is stored internally and never shown. A clean object is promoted out of quarantine. Only a clean version is downloadable, previewable, or comparable: pending is `file_not_ready`, infected or failed is `file_blocked`. |
| F5 | Previews | Inline only for formats a browser renders without running content: raster images, audio, video, PDF, and text or code (served as `text/plain`). SVG, HTML, office, archive, and every other type are download-only (`Content-Disposition: attachment` with an RFC 6266 file name), always with `X-Content-Type-Options: nosniff`. The server renders, transcodes, and thumbnails nothing, and never fetches an external link (no SSRF). |
| F6 | Versions, links, comparison | A file version is immutable (trigger): an object or an external `http(s)` URL without credentials, at most 2048 characters, linked and never copied (FILE-005). A file keeps at most `FILE_VERSIONS_MAX` versions. Comparison is bounded: a line diff for UTF-8 text and code up to `FILE_COMPARE_MAX_BYTES`, otherwise a metadata comparison (name, type, size, checksum, author, time) that says why. |
| F7 | Authorization and lifecycle | Authority is the host's: workspace (members only, never guests), brand, project, task, or comment (through its record; only the comment's author attaches). `record.read` lists and reads; `record.upload` uploads, versions, links, and renames; `record.download` downloads, previews, and compares; `record.trash` trashes; `deliverable.submit` creates and submits deliverables; `review.decide` (4A) decides. Hidden is unknown: an unreadable and an unknown file, version, session, or deliverable are one `not_found` on every route. A revoked grant refuses the next request. Files and deliverables trash, restore, and purge with their host through the 1F lifecycle. |
| F8 | Deliverables | A deliverable (`dlv_`) is contained by its task, with an expected type `any`, `file`, or `url` (TSK-022). Submitting adds a version (a clean file of the same task or a URL) and opens a 4A approval request to named reviewers in one transaction, superseding an open one. The 4A decision drives the state through the `reviewSettled` hook: approved is `accepted`, changes requested and rejected follow, and a withdrawn request returns to `draft`; a stale request is refused. Acceptance records the decision, who accepted, and when, and evidence-locks the deliverable version and its file version (FILE-009); accepted is final. The 4A review queue and the 4B notifications resolve a deliverable through its task, so authority is never duplicated. Task and project lists count accepted versus pending (PRJ-023). |
| F9 | Quotas and retention | `WORKSPACE_STORAGE_QUOTA_BYTES` is a technical limit (plans set it in 10A) counted as used plus reserved bytes in `files.storage_usage`; exceeding it is `usage_limit_reached`. Usage is visible through `GET …/storage` and the signals `files.requests`, `files.jobs`, `upload.completed`, and `file.scan.duration`. Retention stays open (OD-36): files live until their host or workspace is deleted. Purge deletes rows and records each orphaned object as an `object:{key}` external effect that the file sweep deletes idempotently; evidence-locked versions are kept (R-EVIDENCE). No legal retention period is invented. |
| F10 | Honest absences and deferrals | Not built in 4E: collaborative editing (4D), document authoring and document hosts and embeds (4C), connector files (6A, 6C), changes to notification delivery (4B; no new notification types), content search over attachments (OD-31, 5A), `files.evidence_item` (9B), agent artifacts as deliverable sources (8C), attachments during capture (CAP-015 stays refused by 2E until capture adopts upload sessions), plan entitlements for storage (10A), legal holds (OD-37), multipart uploads, and server-side previews. |

## Recorded deviations and clarifications

- **Identifier-free keys.** 0D §15.1 sketched `ws/{workspace_uuid}/{random}`. Keys appear in signed URLs and provider logs, so they carry no identifiers; the row binds the key to its workspace, and the same random part moves from `q.` to `o.` on promotion.
- **Download route.** `files/{file}:download` (current or `?version=`) replaces the sketched `file-versions/{fv}:download`; preview and compare are sibling verbs.
- **Office previews.** FILE-002's "document" formats preview inline only as PDF and text; office formats download, because rendering them would mean server-side conversion of untrusted content.
- **Scanner notifications.** 0D §15.1 said the uploader and admins are notified of infected files; 4B's vocabulary has no such type yet, so 4E shows the blocked state on the file and sends nothing.
- **Retention.** OD-36 stays open; no file ages out on a timer.

## Consequences

Migration `0039_files_deliverables` reverses exactly to 0038. The worker gains the scan job and one recurring file sweep per workspace. The API gains the file, upload, link, storage, and deliverable routes and, in development, the local storage routes.
