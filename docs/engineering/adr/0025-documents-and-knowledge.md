## Decisions

| # | Topic | Decision |
|---|---|---|
| D1 | What a document is and who can see it | A document (`doc_`) is a record in the core envelope: workspace-scoped (no brand) or brand-scoped, optionally attached to one project or one task, and nested under at most one parent page (depth at most `DOCUMENT_DEPTH_MAX`, at most `DOCUMENT_CHILDREN_MAX` children per page and `DOCUMENT_TREE_MAX` pages per tree). A page lives in its parent's brand and attachment. Access is inherited from placement and decided by the same compiled predicate as every record: brand level (or workspace level), the governing project chain of its attachment, and exact-record shares. A document reads through its own record or its share, never through a parent page. Restricted document trees (`access_mode`) and document-level role grants of 0B and 0C are not built in 4C (recorded deviation); they arrive with the sharing and permissions administration phases. |
| D2 | Content model | Content is a block document, version 2 of the rich-text envelope: an ordered list of blocks with stable block identifiers. Block kinds: paragraph, heading (levels 1 to 3), bulleted and numbered lists, checklist (items with a checked flag), quote, code (with a language label), table (rows of text cells with an optional header row), divider, callout, and embed. Inline text carries bold, italic, code, link, and record-reference marks. The server validates, normalizes (canonical key order, trimmed text, generated block identifiers), bounds the size (`DOCUMENT_BODY_MAX_BYTES`, `DOCUMENT_BLOCKS_MAX`, `DOCUMENT_BLOCK_TEXT_MAX_CHARS`), and hashes the canonical form with SHA-256, so equal content always has an equal hash. The editor is a block editor over native controls; 4C adds no editing engine (4D chooses the collaboration engine). |
| D3 | Versions and restoration | Every content save appends an immutable `document_version` (number, title, content, hash, author, kind `save`, `restore`, `suggestion`, or `template`, optional restored-from number, and a change summary of blocks added, changed, and removed). A save names its base version; a stale base is a `conflict` carrying the current version number and nothing is overwritten. Saving content equal to the current hash is a no-op that returns the current version. Restoring never rewrites history: it appends a new version holding the chosen version's content and records which one. At most `DOCUMENT_VERSIONS_MAX` versions exist; past that, saves are refused with a clear issue. Versions are read through the document and exist only while it does (purge removes them; audit keeps hashes). Reading an old version needs read access to the document; restoring needs edit access and an active document. |
| D4 | State, owner, review date | A document is `draft`, `current`, or `stale` (stored), or archived through the record lifecycle. `effective_state` reports `stale` when a `current` document's review date has passed, so nothing claims to be current past its review date; the stored state is never silently rewritten. The owner is an active member who can read the document (the creator at first); changing the owner needs `record.assign`, setting state and review date needs `record.update`, and both are audited and versioned (`If-Match` row version, independent of content versions). A departing owner's documents move to the member chosen in the departure plan. Review dates are bounded (`DOCUMENT_REVIEW_HORIZON_DAYS`). A 4A review request on a document binds to its current content version number. |
| D5 | Links, mentions, backlinks | Links and mentions are registered references in `knowledge.document_reference`, rebuilt from the content on every save (at most `DOCUMENT_REFERENCES_MAX`). Targets are tasks, projects, brands, documents, people, and teams; goals, agents, and external records register when their phases exist. A save checks that every target exists and is readable by the author now; hidden, unknown, and unsupported targets share one `not_linkable` issue. Rendering re-checks every viewer: a reference the viewer cannot read renders as the neutral "Restricted item" token with no title, type, brand, or identifier (IA-46), and a reference whose target was removed renders the same way. Backlinks (`records/{id}/documents`) list only documents the viewer can read, and only when the viewer can read the target. Nested pages form a tree with no cycles (a move never targets the page's own subtree). A mention of a person emits an event the 4B fan-out turns into a notification for them if they can read the document. |
| D6 | Comments, suggestions, reviews | Comments, reactions, following, and reviews work on documents through the 4A host registry (`document` joins `COLLAB_HOSTS`); comments are document-level (anchored comments arrive with 4D). A suggestion (`dsg_`) proposes replacing one block, made by someone with comment access, against a named base version and the base block's hash. The owner or an editor accepts or rejects it. Accepting applies only when the block is unchanged (same hash) and appends a version of kind `suggestion`; otherwise the suggestion becomes `stale` and nothing is applied. A suggestion never changes content by itself and never grants access. At most `DOCUMENT_SUGGESTIONS_OPEN_MAX` are open per document. |
| D7 | Types and templates | Document types are `page`, `brand_brief`, `project_brief`, `sop`, `specification`, `meeting_notes`, `decision`, and `release_notes`. Types constrain placement: a brand brief sits in a brand, a project brief in a project. Typed starter content is built into the product (versioned constants), and creating from a type records the starter's version in the first version's kind (`template`). 4C builds no template catalog, no custom templates, and no installation records (10B). |
| D8 | Embeds | Native: code blocks, tables, checklists, callouts, and links. Images and videos embed by `https` address as a link card; nothing is fetched or loaded automatically, so a document never contacts another site on its own. Files, uploads, previews, and thumbnails belong to 4E: a file embed is refused with `unsupported_embed` until then. Addresses are validated (`https`, no credentials, bounded length). |
| D9 | Export (OD-32) | Markdown and HTML at launch (plain text for a single page is the Markdown body without markup). PDF is not offered: the HTML export carries a print stylesheet so a browser can save a PDF, and generating PDF files belongs to 6D. Export needs `record.export` at view level (not for guests or read-only members by policy), re-authorizes every reference and subpage, is bounded (`DOCUMENT_EXPORT_PAGES_MAX`, `DOCUMENT_EXPORT_MAX_BYTES`), is audited (format and counts, never content), and states what could not be carried (embeds exported as links, unavailable references). |
| D10 | Contracts, lifecycle, boundaries | Events are `knowledge.document.created`, `.version_saved`, `.restored`, `.updated` (state, owner, review date, move), `.mention_added`, `.suggestion_created`, `.suggestion_decided`, and the existing `.source_approved`. Payloads carry identifiers, kinds, and counts only, never titles or content. Archive, trash, restore, and purge follow the record lifecycle: a page's lifecycle carries its subpages, a project's or a task's carries its attached documents, and purge removes versions, references, suggestions, comments, and approvals. A source approval (DOC-017) is an append-only fact about one version made by a person with `record.assign` authority; it stops applying when a newer version is saved, and no search or AI behavior is built here (5A, 7B). 4C builds no file storage (4E), no live editing or presence (4D), no search index (5A), and no notification delivery (4B). |

## Recorded deviations and clarifications

- **No restricted trees.** 0B (`access_mode`, `allow_record_shares`) and 0C (document trees as restricted or granted arrays) describe document-level restriction. Building it changes the shared visibility compiler; 4C inherits placement access instead and keeps the shared predicate untouched.
- **Document-level comments.** Anchoring comments to blocks is 4D's concern with presence and co-editing.
- **No automatic staleness job.** `effective_state` derives staleness at read time; a worker that rewrites states would fabricate history.
- **PDF.** Not offered at launch; see D9 and OD-32.

## Consequences

Migration `0038_documents` reverses exactly to 0037. The Knowledge destination, project and task Documents sections, and document pages become real; the 4A host registry gains a third host.
