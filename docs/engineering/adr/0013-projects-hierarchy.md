## Context

2A is the first product module. It reuses the 1C scope resolver, the 1D permission compiler and preview engine, the 1E registries, and the 1F lifecycle machinery. There is no parallel authority table, status system, hierarchy store, router, or lifecycle path.

## Decisions

| # | Topic | Decision |
|---|---|---|
| P1 | Package and migrations | `@pm/work` is the layer-3 package. Two expand migrations: `0021_work_projects` (schemas `workflow` and `work`, the five seeded platform statuses, every project structure, the project scope column on `access.role_assignment`, the last-manager guards) and `0022_project_relations_templates_recurrence` (schemas `relations`, `templates`, `planning`; recurrence identity on `work.project`; definer functions for the worker and purge). Both have down migrations; the boundary catalog test proves 0022→0021→0020 restore the exact earlier catalogs. |
| P2 | Hierarchy | One parent, same workspace and brand (composite foreign key plus a deferred ancestry trigger). `ancestor_ids` and `depth` are denormalized and guarded: a check ties `depth` to the ancestry length, the deferred trigger checks every row against its parent at commit, and the database ceiling is 32. Commands enforce `PROJECT_DEPTH_MAX` (10, root = 0). A move takes transaction advisory locks on both brand roots in a fixed order, checks cycle and height, then rewrites the subtree in one statement. Descendants are found by a recursive walk on `parent_project_id`, never an array predicate (array operators are not leakproof, so under RLS they cannot use an index). |
| P3 | Authority (AZ-21) | Project collaborators are `access.role_assignment` rows at project scope (`view`, `comment`, `edit`, `manage`), capped by the workspace role. Owner is responsibility: creation, ownership transfer, and restriction write or keep an explicit `manage` grant (`grant_source = project_manager`) in the same transaction. A deferred guard on project, assignment, and membership refuses any commit that leaves an active project without an eligible manager. A restriction anywhere in the chain stops brand, workspace, and implicit role access for the subtree; explicit project grants flow down until the next restriction. Owners and administrators get no bypass. |
| P4 | Visibility | The 1D visibility compiler gains a project branch: it subtracts restricted chains from brand access and adds explicitly granted projects, before pagination and counts. List, count, tree, overview, dependency display, palette, favorites, recents, and breadcrumbs use the same predicate as single-record checks. Previews compute exact deltas with the same code on hypothetical principals, so preview equals enforcement. |
| P5 | Sharing (WSB-008) | One shareability registry (`project` only, levels `view`/`comment`/`edit`, stored `view` = `read`) is consulted by the API and the service; unregistered types are refused even when a `core.record` exists. **Share-only representation:** the project, its criteria items and scope items (intrinsic, non-addressable facts), and exactly the latest verified update's content and public ID. Never phases, milestones, decisions or questions, dependencies, children, recurrence configuration, templates, collaborators, grants, audit or activity, verification history (verifier, time), unverified or older updates, or counts. Each overview section is authorized on its own (a separate authority may show more); commands that a share excludes return `not_found` to a share-only reader; capabilities (`edit_structure`, `relate`, `save_template`, `manage_recurrence`, `verify_update`) follow the same boundary. Unreadable targets: `not_found` (AT-115). Readable without `record.share`, or unshareable type: `forbidden` (AT-050, AT-116). Restricted projects refuse shares unless `allow_record_shares` is on. |
| P6 | Structures | Phases (ordered, active/archived/trash; archive is reversible), milestones (optional phase), criteria (success / definition of done), scope items (scope, exclusion, risk, assumption, constraint), decisions and open questions (`proposed → decided → superseded`; `open → resolved`; cross-kind transitions refused in the database and service). All ranks are `COLLATE "C"` base-62 fractional keys. |
| P7 | Updates (OD-16) | `project_update` and `project_update_verification` are append-only for every application role. Only a human with `project.verify_update` verifies. The latest verified update is the newest update with a verification row. |
| P8 | Completion (OD-13) | Until tasks exist a completed project is 100 % and any other is 0 %, labelled status-based. Overdue, blocked, unassigned, and at-risk sections say they arrive with tasks. |
| P9 | Dependencies (OD-05) | `relations.record_relationship` `blocks` edges. Creation needs `record.relate` on the source and readability of both endpoints; cross-brand edges are allowed on that basis. A workspace advisory lock and a recursive check refuse cycles. On display each counterpart is re-authorized and an unreadable one is omitted entirely. |
| P10 | Templates and duplicate | `templates.template`/`template_version` hold a validated package (schema v1) with at most `TEMPLATE_ITEMS_MAX` items. Serialization keeps project fields, phases, milestones (relative day offsets), criteria, and scope items. People, grants, shares, updates, decisions, dependencies, audit, recurrence, and cross-brand references are never copied, and the response lists them (`not_copied`). `templates` reads `work`; `work` never imports `templates` (an instantiation hook in the service). |
| P11 | Recurrence (OD-14) | `planning.recurrence_series` stores the frozen package in `template_payload`; a trigger makes it immutable. RRULE subset (DAILY/WEEKLY/MONTHLY/YEARLY, INTERVAL 1–366, BYDAY for weekly, BYMONTHDAY for monthly; anything else is refused) in the anchor time zone. Occurrence key = local `YYYY-MM-DDTHH:mm`; `(series, key)` is unique, so generation is idempotent. The hourly `work.recurrence` job discovers due series through a dispatcher definer function, generates at most `RECURRENCE_CATCHUP_MAX` per series per run, rechecks the owner's freshness and authority first, and pauses the series (audited) when the owner can no longer manage the source.. **Definition and UI:** the API takes the structured rule (`frequency` daily/weekly/monthly/yearly, `interval` 1–366, `weekdays` for weekly, `month_days` for monthly, `start` local date-time, `anchor_tz` IANA, `ends` never / after 1–999 / on a local date) and composes the canonical RRULE (COUNT or UNTIL); unsupported combinations are field errors. The series view returns the structured rule, the next occurrence as local intent plus instant, and a status (`active`, `paused`, `catching_up`, `ended`). `project.manage_recurrence` is offered only with `record.create` in the brand (each occurrence is a new project). |
| P12 | Lifecycle | Brand cascades reach every project; a project's own lifecycle reaches its phases, milestones, and decisions, never child projects. Purge is blocked while a child references the parent (`children_remain`). Work routes get lifecycle decisions only through `issueRecordLifecycleDecision` exported by tenancy; a unit test rejects every other caller. Purge removes project grants through a definer function and nulls recurrence sources. |
| P13 | Ownership and departure | `projectOwnerHook` counts and reassigns project ownership, recurrence series, and manager grants in departure plans. The deferred last-manager guard backs this up in the database. |
| P14 | Intake provenance (PRJ-017) | Creation accepts an optional `intake_source` (`form_…`). Only an `intake_form` record the caller can read is accepted; unknown, foreign, and unreadable sources fail identically. The source and `source_kind = form` are recorded; forms themselves are 2E. |
| P15 | API and UI | `/v1/workspaces/{ws}/projects` with ETags, idempotency keys, field-merge edits, and action verbs (`move`, `owner`, `access`, `archive`, `unarchive`, `trash`, `restore`, `purge`, `template`, `duplicate`). Web: the Projects destination (list grouped by brand in multi-brand scope and by status in single-brand scope; archived filter; keyboard tree with type-ahead and Move up/down, Indent, Outdent, Move to…), the project page (header, readable-only breadcrumbs, favorite, recents, section navigation in the fixed order), Overview, Timeline (phases, milestones, dependencies as lists), and Settings. Tasks, Calendar, Documents, Files, Activity, Time, Costs, and Reports are real routes with an honest unavailable state; Tests and Releases are addressable and their tabs absent. |
| P16 | Telemetry | `work.hierarchy.moves` (outcome) and `work.recurrence.occurrences` (outcome). No titles, descriptions, budgets, risks, or endpoint data in labels, logs, or error context; audit records content changes as hashes. |
| P17 | Overview envelope | `GET /projects/{prj}/overview` returns `project_overview`, a computed non-resource composite without a synthetic public ID. It is in the closed `NON_RESOURCE_TYPES` registry (`packages/contracts/src/envelopes.ts`, ADR-0008 B3), built only by `apps/api/src/work/routes.ts` through `nonResourceEnvelope`; the confinement test rejects other constructors, hand-built envelopes, and unregistered types. Nested resource objects keep their real public IDs and individual authorization. |
| P18 | Rich description (0D PL-23) | `work.project.description_rich jsonb` holds rich text version 1 (`{type: "doc", version: 1, content}`: paragraphs of unmarked text). The API, templates, duplicates, recurrence snapshots, and audit hashing use it. Validation at the API (`@pm/contracts/rich-text`) and the database (`tenancy.valid_rich_text`) refuses other nodes, marks, attributes, and versions; the 20,000-character limit applies to extracted text in code points; `null` is the only empty value. Field merges send `base_hash` (RFC 8785, sha256). The 2A editor is a plain multiline control encoding one paragraph per line; 4C adds a rich editor and nodes without migrating stored descriptions. |
| P19 | Recurrence discovery bounds | Registered 0D parameters `RECURRENCE_WORKSPACE_DISCOVERY_MAX` (200, 1–1000) and `RECURRENCE_SERIES_DISCOVERY_MAX` (50, 1–500), injected through typed configuration into the worker; `RECURRENCE_CATCHUP_MAX` (12) stays the per-series occurrence bound. Both discovery layers order by `last_run_at` (stamped on every run; operational, not versioned), so work beyond a batch stays eligible and every due series is reached within a bounded number of runs. Full batches are counted (`work.recurrence.occurrences` outcomes `workspace_batch_full`, `series_batch_full`). |

## Dispositions (Phase 2A pre-commit review 01)

| # | Item | Disposition |
|---|---|---|
| G1 | Project description storage | **Rejected as a deviation; corrected.** Rich description storage is implemented in 2A (P18); the rich editor is deferred to 4C |
| G2 | What a project share shows | **Accepted with the exact boundary in P5**: project, criteria, scope items, and only the latest verified update's content and ID |
| G3 | Recurrence discovery batch sizes | **Rejected as a deviation; corrected.** Registered parameters (P19), no literals |
| G4 | Recursive-walk join plan chosen by volume | **Accepted.** Representative 5,000-project plan evidence is kept (50,000 checked in review); no planner strategy is pinned without production data |
| G5 | Recurrence UI scope | **Rejected as a deferral; corrected.** Daily, weekly, monthly, yearly with interval, weekdays, day of month, anchor date-time and zone, end condition, next occurrence, paused/catching-up/ended state, pause/resume/manual next (P11). 2D may improve ergonomics and task recurrence only |
| G6 | Template catalog management | **Accepted.** 2A provides create-from-project and apply; rename/archive/version management UI is 10B. Each apply and recurrence names the immutable package it used |
| G7 | Followers | **Accepted.** Entirely 4A (PRJ-026); no rows, counts, or UI in 2A |
| G8 | Intake provenance | **Accepted.** Implemented and tested with registered fixtures; real forms and anonymous, routing, and abuse flows are 2E/OD-28 |
| G9 | Screen-reader study | **Accepted.** Automated keyboard, axe, and responsive coverage now; the manual NVDA/JAWS/VoiceOver study stays scheduled for 11E and is not claimed complete |
| P17 | `project_overview` non-resource envelope | **Accepted narrowly** (P17) |

## Consequences

Later modules attach to projects by registering record types and actions at 0B/0C/0D, adding lifecycle adapters under the project, contributing package items to the template serializer, and registering sections in `PROJECT_SECTIONS`. Tasks (2B) replace the status-based completion basis and fill the task-derived Overview sections. Custom statuses (2C) add workspace statuses beside the five platform defaults without changing `status_category`.
