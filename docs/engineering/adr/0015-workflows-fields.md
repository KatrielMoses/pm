## Decisions

| # | Topic | Decision |
|---|---|---|
| W1 | One workflow system | `workflow.workflow` with its statuses and transitions lives in the existing `workflow` schema. `workflow.platform_status` stays the immutable default and is never copied. Evaluation is owned by `@pm/work` (`workflow/transitions.ts`). |
| W2 | Scope and precedence | One record kind and one scope per workflow; at most one active workflow per scope and kind (unique index). Resolution is project → brand → workspace → platform default, in the database (`workflow.resolve_workflow`) and the service (`resolveWorkflow`). A project-scope task workflow applies only to that project's tasks; projectless tasks use their brand's, then the workspace's. Changing a workflow never changes authority. |
| W3 | Status identity | `sts_` public ID, name, description, color, icon, rank, lifecycle, and one fixed category. A trigger refuses category, workflow, or identity changes, and a delete guard refuses removing a status a record uses (current or reopen target). A record's `status_id` references a platform status or a workflow status. The category trigger checks every write, and a newly chosen status must be offered by the workflow that applies now. Archived statuses stay on records until migrated. |
| W4 | Defaults | With no custom workflow, the 2A/2B statuses apply. Any non-terminal status may move to another; Complete into done, Cancel into cancelled, Reopen from a final status to the prior status still offered, otherwise the first planned status. New records start in the first planned status of the applicable workflow (creation, duplicate, template, recurrence). |
| W5 | Transitions | Once a workflow has an active transition, only registered edges are allowed. One evaluator (`evaluateTransition`) serves a generic status edit, Complete, Reopen, the apply command, and previews. For tasks, an edit cannot complete or reopen. For projects, the status edit is the explicit command (2A API). |
| W6 | Required fields | Built-in keys (per record kind) or custom definitions, checked on the final merged record under the record lock before any write. Missing fields are pointer-addressed issues, and the record is unchanged. A field the actor cannot read is never named (`requirements_unmet`). The 2B criteria override does not satisfy workflow-required fields; only a requirement with `allow_manager_override` accepts a manager's reason through the apply command, and the use is audited. |
| W7 | Approvals | `none`, `one_manager` (manage on the record), or `all_named_approvers`. `workflow.approval_request` (`wap_`) binds the record version, transition and version, fingerprint, requester, approvers, and expiry (`APPROVAL_EXPIRY_HOURS`). Decisions are append-only, one per approver. State (pending, approved, rejected, stale, expired, applied, withdrawn) is derived. Any change to the record or transition makes a request stale. Self-approval needs the transition flag and the workspace `self_approval_mode` (OD-20: `auto` allows it only with one active member). Being an approver grants no access; an approver who cannot read the record gets `not_found`. |
| W8 | Apply | Preview returns the evaluation, required fields, approval requirement and open requests, warnings (criteria, subtasks), and a signed fingerprint valid for `TRANSITION_PREVIEW_TTL_SECONDS`. Apply recomputes under the lock, verifies the fingerprint (record version, transition version, workflow version, epochs), consumes an approved request (one-time close), runs step-up for `step_up` transitions, changes status and completion facts, bumps versions, audits, and emits the existing status events. A change that needs confirmation or approval is refused (`transition_requires_review`) outside the apply command. |
| W9 | Configuration lifecycle | Workflows, statuses, transitions, fields, options, and sets are active or archived; archive is reversible. Purge (delete) is refused while referenced: statuses in use, approvals on a transition, values, formulas, transition requirements, or set versions that use a field. |
| W10 | Field types | Exactly text, number, currency, percentage, date, person, label, checkbox, URL, email, select, and formula; the type is immutable (trigger). |
| W11 | Definition scope | Workspace, brand, or project, applying to projects, tasks, or both. Broader fields accumulate. A narrower definition with the same `lineage_id` (created with `shadow`) replaces the broader one for records in its scope. Names are not identity. |
| W12 | Values | One `workflow.field_value` relation per (definition, record), holding validated typed JSON plus normalized typed columns derived by a database trigger, with workspace and brand roots, version, updater, and RLS. Writes use field merge (`base` per field, record version as the ETag) and bump the record version. |
| W13 | Validation | Per-type configuration (length, numeric range and scale, currency, percentage range and scale, date bounds, URL schemes, email normalization, select options, person and label eligibility) and a safe pattern engine (W-pattern below). The database repeats shape and reference checks. |
| W14 | Currency and percentage | Currency is integer minor units plus an ISO 4217 code fixed by the field; a different currency is refused and nothing is converted. Percentage is a decimal in percentage points within −1000 to 1000 with scale 0–4 (invariants). |
| W15 | References | Person values need an active internal member; label values need an active label of the record's brand; neither grants access. Historical identity remains when a person leaves or a label is archived; new selection is refused. Label values are removed when a task moves to another brand. |
| W16 | Options | `fop_` identity; renaming keeps meaning; removing an in-use option needs `replace_with` (bounded by `FIELD_VALUE_BULK_MAX`, repeated until none remain) or archival. |
| W17 | Formula safety | A hand-written tokenizer and parser build a versioned AST (`v: 1`). The language has literals, same-record references `{fld_…}`, `+ - * / & = != < <= > >=`, `and`, `or`, `not`, and a fixed registry (`if`, `coalesce`, `is_empty`, `round`, `floor`, `ceil`, `abs`, `min`, `max`, `concat`, `len`, `lower`, `upper`, `days_between`, `add_days`, `year`, `month`). There is no `eval`, current time, randomness, network, context, or cross-record access. Stored ASTs are re-validated before use. Bounds are `FORMULA_SOURCE_MAX`, `FORMULA_AST_NODES_MAX`, and `FORMULA_REFS_MAX`; the magnitude limit is 1e18 and the scale 12 (invariants). |
| W18 | Formula graph | Explicit `formula_dependency` rows, cycle-checked at save (service) and at commit (deferred trigger), bounded by `FORMULA_DEPTH_MAX`. Results are computed in dependency order from stored values and materialized in the same transaction as any value write to the record. Errors are typed: `missing`, `invalid`, `divide_by_zero`, `cycle`, `overflow`. Results are read-only. |
| W19 | Formula authorization | A formula is readable only where every transitive input is readable. Otherwise it is absent, and `explain` is `not_found`. Explanations name readable inputs and say whether they have a value, never the value. |
| W20 | Visibility | Record readability ∩ applicability ∩ `access.field_policy` (`all_readers` or a minimum level; edit minimum; guest visibility, off by default). Hidden fields are absent from payloads, edits (`not_found`), required-field errors, explanations, and record exports. View visibility is stored metadata (list, board, table, calendar, timeline, gantt) for 3A. |
| W21 | Advanced fields | `primary` or `advanced`. Advanced fields render under "More fields" (a disclosure button with `aria-expanded`), searchable by label, and an error in one expands the group and focuses it. This is presentation only. |
| W22 | Field sets | `fst_` sets with immutable versions (ordered items and presentation overrides). Records attach one version. `via_set` definitions apply only through an attached version. A new version changes nothing on attached records until a manager previews and upgrades. Values of removed fields are hidden, never deleted. |
| W23 | Serialization | `pm.custom-fields` version 1 holds definitions, options, lineage, visibility, formula AST and dependencies, sets and versions, and typed values by public ID. Unknown properties become `extensions`, and unknown types stay opaque; neither is executed. Export → parse → export is canonical-equal (`fields:validate_document`). Files, mapping, jobs, review, and cross-workspace resolution are 6D. |

## Recorded deviations and clarifications

| # | Item | Resolution |
|---|---|---|
| V1 | Project-scope project workflows | Apply to that project itself (the record kind is project), never to child projects; project-scope task workflows apply to its tasks. |
| V2 | Formula recomputation | No queued recomputation: inputs are same-record, so a value write recomputes the record's formulas in its transaction. After a formula definition changes, results carry the old `formula_version`; reads compute the current result until the next write materializes it. |
| V3 | Status migration | Only to an active status of the same category (completion semantics unchanged), only records the caller can read, in batches of `FIELD_VALUE_BULK_MAX`; the response reports what remains. |
| V4 | Purge authorization | The tenancy lifecycle issuer decided `record.purge` as a record action, but 0C defines it at brand or workspace scope (owners and administrators). 2A/2B tests only reached refusals. The issuer now decides purge at the record's brand after a readability check, and the task and project purge hooks remove workflow facts (values, attachments, approval requests and decisions). |
| V5 | `required` on a definition | A required field cannot be cleared once it has a value. Gating a status change on a field is a transition requirement (W6). |
| V6 | Validation patterns | A linear-time Thompson NFA over a subset: literals, `.`, `\d \w \s` and their negations, classes, groups, alternation, and bounded repeats (`PATTERN_REPEAT_MAX` 100, `PATTERN_STATES_MAX` 4000 invariants). There are no anchors (the whole value must match), back-references, or lookaround. |
| V7 | Approval notes | Stored only as a hash on the decision; note text and discussion arrive with comments (4A). |
| V8 | Navigation | Workflows and Custom fields appear in the admin navigation for members; each page decides authority per scope (`not_found` or `forbidden`). Field sets and approvals are reached from those pages and from records. |

## Consequences

- Phase 3A applies view visibility and filters by the typed columns. 4A adds review states and notifications on top of the approval facts. 4E connects deliverable reviews. 6D imports and exports through the canonical document.
- Query plans at 5,000 records × 10 fields (50,000 values) are tested for values, typed sorts, resolution, transitions, statuses, definitions, options, dependencies, approval queues, and set attachments.
