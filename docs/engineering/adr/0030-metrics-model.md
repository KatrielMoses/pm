# ADR-0030: Metrics model (Phase 5C)

Status: **proposed** (decisions recorded before code; implemented; awaiting one clean current-head no-skip CI run on the stacked draft PR).
Builds on ADR-0029 (goals and portfolios: the viewer-computed figures and the health rules), ADR-0028 (search authority and the index-state pattern), ADR-0019 (time), ADR-0022 (capacity), ADR-0026 (deliverables), ADR-0023 (collaboration), the time-zone rules of 0A, and the visibility compiler of 0C §4.5.

**Numbering.** 5C branches from the accepted Phase 5 integration head (`0c9136c`, which already integrates 5A and 5B). It uses migration `0043`, ADR-0030, 0B ADR-38, 0C AZ-38, threats T-63 and T-64, tests AT-269 onward, 0D PL-40, and 0E UXD-30. Phase 5D is delivered in parallel and also needs identifiers after the integration head; the architect's integration step renumbers one of the two sets (as 5A and 5B were). Migration `0042` and everything before it are untouched.

## Decisions

| # | Topic | Decision |
|---|---|---|
| M1 | One authority, applied first | Every figure is computed by `MetricService` in one workspace transaction for the person asking. Each statement joins every counted record (a task, a project, a deliverable's host task) to the `core.record` that governs it and applies the **compiled visibility predicate** (`need: view`, project chains, exact-record shares, brand sensitivity, lifecycle) *before* anything is counted, grouped, ranked, timed, or labelled. There is no second evaluator and no application-side filtering of rows fetched without it. A hidden record contributes to no number, label, order, group, freshness, or timing, and a hidden project or brand named in a request is refused exactly like one that does not exist (`unavailable`). The goal and portfolio figures of 5B and these share the same helpers (`taskFacts`, `loggedMinutes`, the leaf rule), so the two cannot drift. |
| M2 | A definition is a versioned, immutable contract | Each metric has a definition (id, version, name, unit, scopes, window, whether it can be reproduced for a past time, numerator, denominator, sources, time-zone rule, freshness basis, rollup rule, the incomplete-data states it can report, its authorization rule, its drill roles, what it does **not** claim, and its availability). Definitions live in a versioned code registry (`METRIC_DEFINITIONS`); every result carries the definition's version and SHA-256 digest, and a test pins each released digest: changing what a number means is a **new version**, never an edit, and the old version stays computable. This reconciles 0B's `metric_definition` entity as a registry rather than a table: a definition is executable (it names the SQL that computes it), so a database copy could drift from the code that runs, and a digest in every result is the provenance. `current` is the version used when none is asked for. |
| M3 | Computed live; no stored aggregates | A figure is read from the records at the time of the request, never from a stored count, so it always equals the records behind it and its drill-through lists exactly them (a test compares every role's count with the length of its list). 0B's `metric_snapshot` is **not built**: a pre-aggregated value per scope cannot be shared between people without disclosing what some of them may not read, and a per-person copy would be a stale second authority. A report that must freeze a figure for a recipient (5D's `report_run`) stores the result it computed *as that recipient*, with the digest of M2 and the reproducibility block of M8. |
| M4 | What a result says | A result carries: the definition (id, version, name, unit, digest), the scope (workspace, brand, or project with or without its sub-projects), the window in local dates and the zone, `as_of`, a **state** (`complete`, `partial`, `estimated`, `empty`, or `unavailable`), the figure (`value`, and `parts` as numerator and denominator where there is one), a list of **incomplete** reasons each with a code, a count where meaningful, and a plain sentence, the **freshness** (M11), the provenance (sources, authorization `viewer`, evidence `recorded_records`), the **limits** (what it does not claim and who may see it), the **drill** roles with their counts, and the reproducibility block (M8). A figure with nothing to measure is `empty` (never 0% or 100%); a source that does not exist yet is `unavailable` (M12). |
| M5 | Scope and rollup | The scopes are the workspace, a brand, or a project (default with its sub-projects, `subprojects=false` for the project alone). A rollup is always stated in the definition and is a **ratio of sums** (all done over all counted, across projects, brands, or the workspace), a **sum** of counts, a **pooled distribution** (medians and the 85th percentile taken over the pooled records, never averages of group medians), or, for health, the **count of projects in each class** (never a blended class). Breakdowns by project, person, band, category, source, or day are listed with a bounded number of rows (`GROUP_MAX` 50) ordered by what the person can see, then by public identifier, so a hidden row can neither enter nor move the order. |
| M6 | Weighted completion (resolves the OD-13 follow-up) | `project.completion` keeps **version 1** (by leaf-task count, whole percent, half up; paused tasks count, cancelled tasks do not; exactly what 2A and 5B ship) as the default, so goals and portfolios are unchanged. **Version 2** weights each counted leaf task by its estimate in minutes: numerator the estimate of done leaf tasks, denominator the estimate of counted leaf tasks, rolled up as a ratio of sums. A counted task with no estimate carries **no weight**, is counted in `unestimated_tasks` and listed by the drill role `unestimated`, and makes the state `partial`; it is never given a guessed estimate. When no counted task has an estimate the result is `empty` with `no_estimates`, never a silent fall back to version 1. A leaf is a task with no child the viewer may read, so hidden children never change it. A future change of the default is an explicit architect decision recorded against OD-13. |
| M7 | Time zone and windows | A windowed metric takes `from` and `to` as **local calendar dates in the workspace zone** (default: the last `METRICS_DEFAULT_WINDOW_DAYS` ending today; at most `METRICS_WINDOW_DAYS_MAX`). The window is the half-open instant range from local midnight of `from` to local midnight after `to`, computed in the database (`AT TIME ZONE`), so a day that gains or loses an hour at a clock change counts the hours that passed and a window across the change has the right number of local days. Daily buckets are local days. Age is measured in whole 24-hour periods and does not depend on the zone. The zone used is part of the result. Nothing uses the viewer's profile zone, so two people, an export, and a dashboard agree. |
| M8 | Historical reproducibility | A metric marked historical (completion, created versus completed, cycle time, time in status, age, planned versus actual) accepts `as_of` (an instant with an offset, not in the future) and reproduces the figure from recorded history; a metric that describes now (health, attention, planned versus completed, workload, time budget, deliverable acceptance, freshness) refuses a past `as_of` (`not_supported`). Reproduction rebuilds **status** from the ledger (M9); attributes that are not versioned (a task's estimate, due date, which tasks are leaves) are read as they are now, and the result says so (`current_structure`). Every result carries `definition_digest` and a `result_digest` over its definition version, scope, window, `as_of`, state, figure, parts, incomplete reasons, groups, and drill counts (not freshness): the same inputs give the same digest on every read while the records are unchanged, and a test shows that hiding or showing records the viewer cannot read restores the digest exactly. |
| M9 | The status ledger | The one input that cannot be recomputed from current state is how long a task spent in each status. `metrics.task_status_span` is an append-only ledger written by triggers **in the task's own transaction** (creation opens a span; a change of status or status category closes the open span and opens the next), so no write path can miss one. A span holds a status category, two instants, and a `basis`: `recorded` (written as it happened), `assumed` (written by the migration for a task that existed before the ledger: one span in its status, a finished task at its completion time), or `repaired` (written by reconciliation, M10, starting when the disagreement was found, never backdated). It holds **no** brand, project, lifecycle, or permission key: every read joins the task's `core.record` and applies M1. Deleting a task, and tombstoning a purged record, remove its spans in the same statement. A figure that needs earlier history excludes assumed history and says so (`history_unavailable`, `assumed_history`) instead of guessing. |
| M10 | Bounded, resumable, observable reconciliation | The trigger cannot normally disagree with the tasks; `metrics.reconcile` (every five minutes) is the proof and the repair. Per workspace it claims a **lease** (`METRICS_RECONCILE_LEASE_SECONDS`, so two workers never overlap and a crashed worker's workspace returns), checks at most `METRICS_RECONCILE_BATCH_MAX` tasks after its saved keyset position (`scan_after`), locks the open spans of tasks that look in disagreement, looks again with a fresh view (so a task that moved meanwhile is not repaired and its new span is never closed), closes and reopens the rest as `repaired` in two statements, and records progress and repairs in one transaction. A pass completes when a step finds fewer tasks than the batch; the next pass is `METRICS_RECONCILE_INTERVAL_MINUTES` away. A failure keeps its state: attempts, a short code (`source_error` or `timeout`, never a message), and a doubling backoff (`METRICS_RECONCILE_BACKOFF_SECONDS`, capped at the interval); after `METRICS_RECONCILE_MAX_ATTEMPTS` the workspace is reported `failing`. Purged records are not repaired. Discovery is payload-free (`exec_dispatch.discover_metrics_work` returns workspace identifiers only). An administrator can ask for a pass now (`POST metrics:reconcile`, `workspace.configure`); the API may only move the schedule. Signals: `metrics.requests`, `metrics.query.duration`, `metrics.reconcile.jobs`. |
| M11 | Freshness | Every result says how current its inputs are for this person: `current`, `catching_up` (a pass is pending or overdue), or `degraded` (a reconciliation is failing, or a derived source has failed items), with the time of the data and, for ledger metrics, the reconciliation state, the last success, and how many of the person's tasks have assumed or repaired history. The `data.freshness` metric reports each derived source (status history, the search index of 5A, goal recalculation of 5B) with counts **only over records the person can read**, so waiting or failed work on hidden records leaves no trace; the reconciliation's own times are workspace-level and say nothing about any record. A degraded or lagging source shows a banner on the page, never a complete-looking figure. |
| M12 | Incomplete, estimated, and unavailable | Incomplete reasons are part of the definition (`no_tasks`, `no_estimates`, `unestimated_tasks`, `history_unavailable`, `no_start`, `small_sample`, `undated_tasks`, `no_time_logged`, `no_time_budget`, `drafts_excluded`, `owner_unknown`, `people_hidden`, `truncated`, `current_structure`, `assumed_history`, `catching_up`). A distribution with fewer than `METRICS_SAMPLE_MIN` records is shown and labelled `small_sample`. A scope larger than `METRICS_SCOPE_TASKS_MAX` is refused (`too_large`) rather than answered partially without saying so. **Test results** (`quality.tests`, from 9B) and **money and AI spend** (`cost.spend`, from 7A) have definitions and no source: they return `unavailable` with the phase that provides them, never 0 and never an estimate from other activity. |
| M13 | The metrics | `project.completion` (v1, v2, M6); `project.health` (v1: the 5B rules unchanged, with their thresholds, reasons, and incomplete states, judged per visible project; the declared health is never overwritten); `work.attention` (v1: open tasks that are overdue, due in the next 7 local days, blocked by an open readable task, stale by the OD-17 thresholds, or without an active assignee); `work.planned_vs_completed` (v1: tasks due in a window, split into completed by the end of the window, completed after it, and not completed); `work.created_vs_completed` (v1: per local day; a completion is each entry into a done status); `work.cycle_time` (v1: from the first **recorded** active status after the previous completion to each completion, median, 85th percentile, mean, extremes; a task finished without ever being active, or before the ledger, is excluded and named); `work.time_in_status` (v1: seconds per status category inside the window); `work.age` (v1: open tasks by band of whole days, median and 85th percentile); `work.workload` (v1: open tasks and remaining estimate per active assignee, each task once in the total); `time.planned_vs_actual` (v1: for tasks finished in a window, estimate against stopped time); `cost.time_budget` (v1: logged time against each project's time budget); `deliverable.acceptance` (v1: deliverables by review state and the share accepted of those submitted); `data.freshness` (v1). Two meanings of "blocked" are kept apart on purpose: health v1 keeps 5B's (an open blocker or a paused status), attention v1 uses the 2D task signal (an open readable blocker); aligning them is a new version, not a silent change. |
| M14 | No business outcome from activity (RPT-025) | Every definition states what it does not claim, and every result carries it. Completion measures tasks finished, not value delivered; cycle time and time in status are elapsed time, not effort or a person's speed; workload from estimates is not capacity (3E data is not used) and ranks nobody's performance; acceptance records a reviewer's decision, not an achieved goal; health is an explained rule over dates, status, blockers, and time. No figure is estimated from other activity, no metric attributes an outcome to an activity, and nothing here forecasts. |
| M15 | Drill-through from the same selection | `GET metrics/{id}/records?member=<role>` lists the records a count is made of: tasks, projects, or deliverables with their host task, through the same statement fragments that counted them, so the list and the count are the same set by construction. Items carry the public identifier, title, brand, project (when visible), status, and due date. Paging is by a signed keyset cursor (one person, one request; `cursor_invalid` otherwise; offsets are not used) up to `METRICS_DRILL_RESULTS_MAX`, with a page of at most `METRICS_DRILL_PAGE_MAX`. A role a person may not see (`unassigned` for a guest) is refused like an unknown one. The workload drill takes `person` for members only. |
| M16 | Exports and dashboards share the authority | `GET metrics/{id}/export` returns the same figure as CSV (field and value rows: definition, version, digests, scope, window, `as_of`, zone, state, freshness, the figure, parts, incomplete reasons, groups, and the record counts per role) with formula-injection neutralization, `private, no-store`, and `nosniff`. The dashboards and scheduled reports of 5D must call `MetricService` and never compute a figure of their own. |
| M17 | API, bounds, and limits | Routes under `workspaces/{ws}/metrics` (PL-40): catalog, one metric, its records, its export, and the reconciliation request; all private and uncached; reads carry no `Idempotency-Key` (they change nothing). One rate policy `metrics.member` (`METRICS_RATE_PER_MINUTE`). Thirteen bounds, owner 5C: `METRICS_WINDOW_DAYS_MAX`, `METRICS_DEFAULT_WINDOW_DAYS`, `METRICS_DRILL_PAGE_MAX`, `METRICS_DRILL_RESULTS_MAX`, `METRICS_SCOPE_TASKS_MAX`, `METRICS_SAMPLE_MIN`, `METRICS_RATE_PER_MINUTE`, and the six `METRICS_RECONCILE_*` bounds. No action, identifier prefix, or event is added. |
| M18 | Where metrics live in the product | The page `/workspaces/{ws}/metrics` (members; the API serves any person only what they may read) shows one figure at a time with its state in words (never colour alone), the rule behind it ("How this is counted"), what is missing, a freshness banner, tables of any breakdown (stacked cards at 320 px), the records behind it by role, and the export. The whole state (metric, version, brand, project, window, record role) is in the address. Keyboard only, 320 px and 200% zoom, forced colours, reduced motion, and revocation are tested in the browser. |
| M19 | Cost | Figures are computed per request from indexed relations in one workspace (a scope above `METRICS_SCOPE_TASKS_MAX` is refused), so there is nothing to keep warm and idle cost is nil; the only recurring work is the reconciliation, which reads one batch per workspace per five minutes only while a pass is due. Dashboards that refresh many figures should request them together and rely on `private, no-store` only for freshness, not as a license to poll. |
| M20 | Honest absences | Not built in 5C: dashboard layout, widgets, saved or scheduled reports, and PDF export (5D); external adapters and integrations (6x); AI analytics and forecasting (7x); test and defect sources (9B-9D); money and AI spend sources (7A); fiscal calendars (DQ-39); capacity-versus-workload comparison (3E data stays separate); a per-person performance view; a historical workload (assignment history is not used); a historical hierarchy or estimate; stored metric snapshots (M3); and a change of the default completion basis (M6). |

## Engineering finding recorded with this phase

Migration `0041` (5A) queued "every existing source row" for indexing with `INSERT ... SELECT` from the source tables. The migration role is subject to the forced tenant row-level security of those tables and read no rows without a workspace context, so on a database that already held records the statement queued nothing and records created before 5A were not searchable until next edited (verified: after rolling 0041 down and up over one task, `search.index_status` was empty, and search reported `complete`). **Corrected (review 01):** `0041` now lifts the force on the eight source tables for that one read inside the migration transaction, queues every row (idempotent), checks the deferred keys, and forces security again; no application role, policy, or runtime query changes. `search-backfill.test.ts` starts from a database that holds records in two workspaces (restricted, trashed, purged, and deleted records, documents, files, comments, deliverables), applies the migration, proves the index says `catching_up`, then finds every record without editing it, and is idempotent on re-application. Migration `0043` uses the same mechanism for its own backfill.

## Consequences

Migration `0043_metrics_model` reverses exactly to 0042 (two tables, the task triggers and their functions, the discovery function, and the schema). The API gains the metrics routes (PL-40) and the worker gains `metrics.reconcile`. Existing tasks receive one assumed span at migration time, so cycle time, time in status, and the figures that need earlier history report them as incomplete until new history accumulates. Adding a metric later means adding a definition and its computation behind the same authority, never a second reader of records; changing a released definition means a new version.
