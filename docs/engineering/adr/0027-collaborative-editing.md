# ADR-0027: Collaborative editing (Phase 4D)

Status: **proposed** (decisions recorded before code; implemented; awaiting one clean current-head no-skip CI run on the stacked draft PR).
Extends ADR-0025 (documents and knowledge, 4C), ADR-0026 (files and deliverables, 4E), ADR-0023 (reviews, 4A), and ADR-0024 (notifications, 4B).

**Numbering.** 4D integrates 4C and 4E first (merge commit "Integrate 4E (files and deliverables) after 4C"). It uses migration `0040`, ADR-0027, 0B ADR-35, 0C AZ-35, threat T-53, tests AT-230 onward, and 0D PL-37. Migration `0038` (4C) and `0039` (4E) are untouched.

Accepted sources (recorded before code):
- 0A: DOC-011 (collaborative editing) and COL-011; OD-30 (realtime collaborative editing) is **resolved here**, replacing its "safe default" with a bounded live mode that falls back to that safe default.
- 0B: ADR-35. `knowledge.edit_draft`, `knowledge.edit_session`, and `knowledge.edit_op` (migration 0040).
- 0C: AZ-35 (no new actions: `record.read` joins and observes, `record.update` writes); T-53.
- 0D: PL-37 (live-edit bounds, signals, rate policy); 0E: UXD-17 (presence) and UXD-18 (honest states).

## Decisions

| # | Topic | Decision |
|---|---|---|
| C1 | Engine: server-sequenced block operations, no bespoke CRDT/OT | The proven model is the **central-sequencer** one (a single authority assigns a total order; clients are optimistic and converge by replaying that order), the model behind Figma, Linear, and Notion editing. The document is already a list of blocks with stable identifiers and canonical hashes (ADR-0025 D2), so an operation is one of four **block-level** commands: `insert`, `replace`, `delete`, `move`. There is no intra-block text merge, no tombstones, and no vector clocks. **Rejected:** Yjs/Automerge (the CRDT state would carry every reference and every historical character to every participant, so the restricted-reference redaction of IA-46 and the per-viewer permission evaluator could not be applied to the data in transit, and a CRDT history is a second, unauditable source of truth beside the immutable versions); an external provider (out of scope for 4D); a hand-written text OT (unbounded). |
| C2 | Deterministic conflict handling | Every operation carries the **block hash it was based on** (`replace` and `delete`) or the anchor block (`insert`, `move`). The server applies operations one at a time under the document row lock, in arrival order. An operation whose base hash no longer matches, whose block is gone, or whose anchor is gone is **rejected** with the current server block, never silently merged or dropped: the client keeps its draft of that block and offers "keep mine" (a new `replace` against the current hash) or "take theirs". Accepted operations get a gapless per-document `seq`. Because clients apply only server-sequenced operations and rebase their pending ones over them by the same rule, every client converges to the server's block list. |
| C3 | Durable boundary: checkpoints are 4C versions | Live operations edit a **draft** (`knowledge.edit_draft`), never a version. A **checkpoint** appends one immutable `document_version` through the same code path as `saveContent` (canonical parse, restricted-reference restore, reference check, `appendVersion`, `syncReferences`, audit `document.saved`, event `knowledge.document.version_saved`, mention events). A checkpoint happens on an explicit save, when the last live session leaves, and when a session starts after every earlier session expired and the draft differs from the current version. The audit trail records the content hash and the contributor count, never keystrokes or cursor heartbeats. Restore, suggestions, review approval of a version, and exports see only versions, so none of them can see an unsaved draft. |
| C4 | Version and permission evaluator on every operation | Every request (join, operation, poll, heartbeat, leave) loads the document through the one compiled level and requires `record.update` (editing) or `record.read` (observing) **at that moment**. A revoked share, a role change, an archive, a trash, or a purge refuses the next request (`not_found` or `document_archived`), and a refused editor's session ends. The draft opens from the current version and records its `base_version`; a non-live save or restore, or a suggestion applied while a live draft holds unsaved operations, is refused with `live_edit_in_progress` (the non-live path stays correct and versioned); once no session is live the draft is checkpointed or discarded first. |
| C5 | Restricted references | Operations carry the viewer's redacted view. Incoming `rst_` tokens are restored against the draft's content exactly as a save restores them (a token must name a reference the draft already holds). Outgoing operations are redacted **per viewer** through the same resolver as `documentView`. A viewer therefore never receives a hidden record identifier, label, or content, and never removes a link they cannot read. |
| C6 | Transport: HTTP command plus ordered long-poll | `POST …/live:join`, `POST …/live/ops`, `GET …/live/events?after=seq` (bounded long-poll, at most `LIVE_POLL_WAIT_SECONDS`), `POST …/live:heartbeat`, `POST …/live:leave`. Poll and operations are re-authorized every call. No WebSocket server, no new infrastructure, no sticky routing, and an idle proxy cannot hold a revoked editor open. The cursor is the `seq`, so a reconnect resumes with `after=<last seq>`; an operation log older than the retained window answers `resync_required` with a full snapshot. |
| C7 | Operation idempotency and ordering | Each operation carries a client-chosen `opId` (unique per session) and the client's last seen `seq`. A retried `opId` returns the original result (so a lost response is safe), and a client may send at most `LIVE_OPS_BATCH_MAX` operations per request. Operations from one session apply in the order sent. |
| C8 | Session lifecycle and presence | A session (`ses_`) belongs to one principal and document. It is `active` until `expires_at` (`LIVE_SESSION_TTL_SECONDS`, renewed by a heartbeat, a poll, or an operation), then stale: a stale session is excluded from presence and refused by every call at once, and its row is deleted by the next join to the same document, by leave, and by purge (the number of rows per document is bounded by `LIVE_SESSIONS_MAX`, so no sweeper is needed). At most `LIVE_SESSIONS_MAX` live sessions per document and `LIVE_SESSIONS_PER_MEMBER_MAX` per person; beyond that a join is `live_capacity` and the client edits in non-live mode. Presence holds a display colour index, the block the person is in, and the caret block only; never text. |
| C9 | Presence is permission-safe and ephemeral | A viewer sees only sessions of members they are allowed to see by name (the same member visibility as `peopleOf`; **guests and share-only viewers see no one else's presence**, only that edits arrive) and only for a document they can read. Another person's display name appears only when the viewer may see that member, otherwise the session is omitted (never "someone"), so a hidden editor's existence is not disclosed. Presence rows are deleted on leave, on expiry, and on purge, are never audited, and are never copied into events or notifications. |
| C10 | Fallback to versioned non-live editing | If the join is refused (`live_capacity`, `dependency_unavailable`, rate limit), the workspace setting `DOC_LIVE_EDITING=off`, the poll fails repeatedly, or the browser is offline, the editor stays a plain 4C editor: autosaved local draft in the browser, and **Save** uses the optimistic `base version` token and, on conflict, the 4C conflict view (ST-06). Offline edits are kept as a local pending queue and replayed on reconnect (C2 applies); if the base moved too far or `resync_required`, the user's pending blocks are offered against the new snapshot, never discarded. |
| C11 | Compatibility | Comments, reviews, and suggestions anchor to block ids and hashes, which operations never change except by an explicit `replace` (a suggestion on a changed block becomes stale, as in 4C). Mention events and 4B delivery fire only at a checkpoint, from the saved version (4B owns delivery). A file embed block is a 4C `embed` block whose URL is a link; storage stays 4E-owned, and 4D adds the join below. |
| C12 | The 4C and 4E join | 4C left file embeds to 4E and 4E left document hosts to 4C, so 4D closes both. A document is a file host (`host_kind` `document`, workspace-scoped documents included): `record.read`, `record.upload`, `record.download`, and `record.trash` are decided through the document's own level (placement, project chain, exact-record share), and files trash, restore, and purge with the document and its subpages (`documentAdapter.children` and `purgeFileFacts`). A comment on a workspace-scoped document may carry files, so a comment host's brand is optional. A **file embed** is a 4C `embed` block of kind `file` whose `url` is the public identifier of a file attached to that very document (never an address; an address is still `unsupported_embed`). A save, a live operation, or an applied suggestion that introduces one is refused (`invalid_file`) unless the file is active and attached to the document, and an embed already present never blocks a later save when its file has since been trashed. Viewers receive card facts (name, source, type, size, scan state) only for attached, active files, never a URL; preview and download remain 4E's routes, each authorized on its own, and exports say a file was not included. Storage, scanning, and quotas stay 4E's. |
| C13 | Honest absences | Not built in 4D: search (5A), external collaboration providers, agent editing (8C), per-character cursors and selections of text, intra-block text merging, voice or video, presence outside documents, and comments anchored to a passage (4C's ADR-0025 D6 pointed them at 4D; no catalog requirement owns them, so comments stay document-level and block ids keep them possible later). Two things a checkpoint cannot do: attribute the version to every contributor (the person who saves or leaves last is its author; the audit trail counts contributors) and notify mentions as each editor typed them (mention events fire once, from the saved version). |

## Consequences

Migration `0040_collaborative_editing` reverses exactly to 0039 (the three live tables, and the document host kind on files and upload sessions with the comment-host brand relaxation). The API gains the live routes (join, operations, events, heartbeat, checkpoint, leave); the worker is unchanged. Operation logs are pruned at each checkpoint and removed with the document. Live editing is bounded by explicit limits and degrades to the 4C editor, so OD-30's safe default always remains available.
